# Мотивация
Трейсинг нужен чтобы команда могла видеть полный путь заказа от нажатой кнопки на сайте до обработанного заказа, а не отдельные логи 

Чем может помочь:
1. Быстрое расследование инцидентов по order_id или trace_id, будет явно видно откуда куда запрос шел, сколько времени занял каждый промежуток и где прекратилась работа.
2. Поиск узких мест. Будет легче найти где запрос потратил больше всего времени выполнения и четко оптимизировать это место.
3. Для бизнеса будет проще расследовать инциденты, сократится время ответа клиенту на жалобу.
4. Снизится риск потери крупных контрактов из-за непрозрачности процессов.

Метрики:
1. Время решение инцидента от клиента.
2. Среднее время расследование багов и инцидентов.
3. Кол-во потерянных заказов.
4. Кол-во зависших заказов.

# Предлагаемое решение
Внедрить распределенный трейсинг на базе OpenTelemetry и Jaeger
Jaeger будет хранить, показывать и искать всю информацию, а OpenTelementry позволяет её собрать и отправить.
Нужно внедрить единый trace id который будет от нажатия кнопки на фронтенде до базы данных и всех других систем доходить.

Нужно внедрить 
1. OpenTelemetry SDK в API CRM/MES
2. OpenTelemetry для HTTP клиентов и серверов
3. OpenTelemetry в воркеры MES
4. Передачу trace_id в RabbitMQ и из него

Путь трейса
1. CRM API принимает заказ, создается trace id, сохраняет информацию в базу данных, кладет сообщение в RabbitMQ вместе с этим trace id
2. MES RabbitMQ worker обрабатывает сообщение, использует переданный trace id, сохраняет в базу информацию
2. CRM получает информацию, что обновился заказ и после этого использование этого trace прекращается

# Компромиссы
1. Мониторинг не решит все проблемы бизнеса, это лишь инструмент который позволит легко найти и увидеть ошибки, надо будет настроить бизнес процессы для того что их заранее находить и исправлять.
2. Трейсинг может быть дорогим, поэтому стоит заранее посмотреть размер одного трейса и обсудить время хранения таких трейсов.
3. Трейсинг не заменит логи, это разные вещи для разных целей, с трейсингом удобно рассматривать прицельно нужные операции, но общую картину в целом стоит смотреть через логи и метрики.


# Безопасность 
1. Jaeger должен быть доступен только внутри рабочего кластера\своего облака. 
2. Стоит ограничить доступ к этому k8s namespace для не devops специалистов.
3. Выдать личные учетки для входа в сервис.
4. Использовать HTTPS TLS 1.3 при передаче данных
