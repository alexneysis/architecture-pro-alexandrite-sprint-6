# Мотивация
1. Уже сейчас существуют проблемы в продукте, заказы теряются, скорость обработки заказов медленная, скорость загрузки страниц низкая, пользователи жалуются на ошибки и недоступность сервиса. Это всё можно было увидеть заранее благодаря мониторингу, но его нет. Поэтому нужно внедрить мониторинг, чтобы в будущем можно было заранее выявлять проблемы и устранять их до того, как они повлияют на пользователей.
2. Продукт использует подход микросервисной архитектуры, поэтому чтобы узнать что происходило в момент времени по нужно запросу нужно будет переключаться между разными серверами, что неудобно и неэффективно. Поэтому нужно внедрить мониторинг, чтобы можно было видеть всю картину происходящего в системе в одном месте.
3. Благодаря микросервисной архитектуре тяжело отслеживать как запрос шел по системе, какие сервисы были задействованы, сколько времени заняла обработка запроса и где возникли ошибки. Поэтому нужно внедрить мониторинг (трейсинг), чтобы можно было отслеживать путь запроса по системе и выявлять узкие места.
4. Отслеживать внешнее API, чтобы понимать сколько запросов приходит, сколько времени занимает их обработка и сколько ошибок возникает. Сейчас нет никакой информации насколько сильно нагружено API и как оно работает, поэтому нужно внедрить мониторинг, чтобы можно было отслеживать его работу и выявлять проблемы.
5. Повысить стабильность релизов, это даст метрики которые можно заранее отслеживать и на основе которых можно будет принимать решение о том, готов ли релиз к выпуску или нет. Сейчас релизы выпускаются без какой-либо информации о том как они работают, поэтому нужно внедрить мониторинг, чтобы можно было отслеживать работу релизов и выявлять проблемы.
6. Мониторинг может подсветить места которые требуют больше внимание и приносят больше проблем бизнесу.

# Выбор подхода к мониторингу
1. Для мониторинга воркеров лучше использовать четыре золотых сигнала. Это позволит отслеживать насколько они загружены, сколько времени занимает обработка задач, как долго задачи находятся в очереди и сколько ошибок возникает. 
2. Для API (CRM, MES) лучше RED подход. Это позволит отслеживать сколько запросов приходит, сколько времени занимает их обработка и сколько ошибок возникает.
3. Для мониторинга микросервисов лучше использовать распределенный трейсинг. Это позволит отслеживать путь запроса по системе, какие сервисы были задействованы, сколько времени заняла обработка запроса и где возникли ошибки.
4. Для инфраструктуры (RabbitMQ, DB, Redis) использовать USE подход. Это позволит отслеживать насколько ресурсы используются, перегружены и сколько ошибок.

# Какие метрики и в каких частях системы будем отслеживать
RabbitMQ
1. Количество сообщений в очереди.
2. Кол-во сообщений в DLQ
API
1. RPS на пользователя. Поможет понять от каких клиентов больше всего нагрузки на систему и найти аномалии в поведении клиентов.
2. Response time P95, p99. Поможет понять насколько быстро обрабатываются запросы и выявить узкие места в системе.
База данных
1. QPS чтение/запись. Поможет понять распределение нагрузки на базу данных и выявить узкие места в системе.
2. Кол-во соединений.
3. Размер базы данных. Можно соотнести план с фактом по нагрузке на базу данных и корректировать планирование ресурсов.
4. Slow queries.

Worker
1. Длительность расчета заказа в MES в секундах.
2. Время нахождение задачи в очереди в секундах до того как воркер начал её обрабатывать MES.
3. Количество ошибок при обработке задач MES.

Разное
1. Кол-во заказов на статус, среднее время нахождения заказа в статусе. Поможет понять где застревают заказы и выявить узкие места в системе.
2. Кол-во застрявших заказов в системе.
3. Стоимость расчета заказа в MES. Например соотношение кол-во полигонов на время расчета заказа. Позволит увидеть деградацию производительности заранее.

# План действий
1. Изучить какие технологии представлены на рынке и с какими знакомы работники команды. Выбрать подходящие технологии для мониторинга.
2. Развернуть выбранные технологии в тестовой среде и протестировать их работу. Развернуть TSDB, систему сбора и отправки логов\метрик, систему визуализации и систему оповещений, систему трассировки. Выделить роли и настроить доступы.
3. Добавить сбор метрик с инфраструктуры (EC2, RDS, Redis, RabbitMQ)
4. Добавить сбор метрик с микросервисов (API, MES, CRM)
5. Внедрить мониторинг в production среде.
6. Добавить бизнес дешборды в системе визуализации.
7. Добавить перечисленные метрики в систему мониторинга.
8. Настроить алертинги на критические метрики.

# Показатели насыщенности
1. Выше 90% CPU более 5 мин
2. Выше 90% памяти более 5 мин
3. Выше 80% подключений к базе данных от максимума
4. API response time P95 > 1 секунда
5. HTTP 500 ошибки > 5% от общего числа запросов
6. Кол-во сообщений в DLQ > 5 шт
7. Кол-во сообщений в очереди > N шт (N зависит от нагрузки на систему, нужно будет определить опытным путем)
8. Время нахождения задачи в очереди > 1 часа (зависит от нагрузки на систему, нужно будет определить опытным путем)
